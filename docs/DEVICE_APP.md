# 패스키 없이 현재 앱을 승인하는 순서

1. 기존 자료실 주소에서 로그인하고 **기기 승인 요청**을 한 번 누릅니다. 패스키 팝업은 없습니다. 승인 대기와 공개 기기 ID가 나오며 자료는 없습니다. 이 창은 닫거나 새로고침하지 마세요.
2. Supabase Table Editor의 vault_app_credentials에서 화면과 같은 device_id 행을 찾습니다. 운영자는 요청자가 본인인지 별도로 확인한 뒤 그 행의 approved만 true로 변경하고 저장합니다. 행을 직접 추가하지 않습니다. 예전 패스키 행이 있더라도 현재 화면의 ID만 대조합니다.
3. 그대로 열린 자료실에서 **등록 기기 확인**을 누릅니다. 현재 앱의 임시 키 서명을 서버가 검증하고 승인 상태를 확인하면 기존 메모 화면을 엽니다.

다시 확인: 승인 전 메모 없음·직접 API 403, 승인 뒤 본인 메모 정상·B의 A 메모 404, approved=false 변경 후 다음 보호 요청 403입니다. 5분 확인값이 만료되면 같은 창에서 등록 기기 확인을 다시 누릅니다. 새로고침·로그아웃·창 닫기에는 새 키로 새 승인 요청이 필요합니다. 설치는 승인 여부에 영향을 주지 않습니다.

이것은 RAM 키를 가진 현재 앱 인스턴스 승인입니다. 영구 물리 기기 식별·하드웨어 보증·제공 엔진의 승인 계약을 대신한다고 주장하지 않습니다. 기기 ID는 서버가 검증한 공개 키의 SHA-256 앞 16자리입니다. 서버 표에 공개 키만 저장합니다. 개인키는 내보내기 불가이며 브라우저 저장소에 쓰지 않습니다. 일회용 challenge는 소유자·등록/확인 종류·2분 만료·사용 여부를 RPC에서 대조합니다. 서명은 앱 origin·종류·challenge·공개 키에 묶입니다.

서비스 경로: GET/POST /api/device-enrollment, GET/POST /api/device-check, GET /api/device-status. status 조회나 설치 표시만으로 자료를 열지 않습니다. 공개 앱 캐시는 오프라인 안내·manifest·아이콘만 보관합니다. 2026-10-14 실제 PC에서 설치 앱의 승인 전/후·메모 사용·오프라인·철회/복원·승인 전 API 403·B의 A 메모 404·B 한 건 백업/복원 검증을 사용자 확인 완료로 기록했습니다. 상세 결과는 README의 사용자 직접 검증 완료 표를 봅니다. 심판 결과는 아직 미확인입니다.

기존 콘솔 localStorage 토큰 추출 방식은 사용하지 않습니다. 로그인 후 제한된 window.자료실요청(path, method, body)로 서버 응답을 시험할 수 있습니다. 승인 전에는 확인값을 붙이지 않아 서버 403을 확인하고, 승인 후에는 현재 메모리의 확인값을 붙입니다. 이 도우미는 권한을 만들거나 승인 전 자료를 표시하지 않습니다. 토큰은 함수 안에 남습니다. 메모 응답 본문은 콘솔에 노출하지 않습니다. B 로그인과 승인 후 실제 A UUID로 GET을 보내 HTTP 404인지 확인합니다.
