# 11단계 접속 앱 준비와 서버 승인

이 기능은 새 SQL 적용 후 운영 화면에 배포합니다. 설치는 승인으로 취급하지 않습니다. 기존 주소·메모·공지·백업·구역 규칙은 보존합니다. 소유자 검사는 최종 API에서 계속 수행합니다.

## 먼저 운영자 설정

1. Supabase 기존 프로젝트 → SQL Editor → New query에서 `supabase/step11_devices.sql` 전체를 붙여 넣고 Run을 누릅니다. 기존 notes·공지·백업·감사 행이나 이전 권한을 바꾸지 않습니다. 세 개의 비공개 기기 표와 일회용 challenge 소비 함수만 추가합니다.
2. SQL 성공을 확인한 뒤 준비한 11단계 브랜치를 main에 반영하고 배포합니다. SQL 적용 전에는 main을 바꾸지 않아 기존 사용을 유지합니다.
3. 운영자가 승인 요청 기기의 사용자·기기 ID를 별도로 확인합니다. 요청 화면에 나온 공개 deviceId와 `vault_app_credentials.device_id`를 대조하고 그 행의 `approved`만 true로 변경합니다. 승인 버튼이나 클라이언트 본문의 approved/role 값을 권한으로 쓰지 않습니다. 일반 계정은 이 표를 읽거나 변경할 권한이 없습니다.

## 사용자 화면 순서

1. 기존 자료실에서 이메일 로그인을 합니다. 로그인 토큰은 메모리에서만 사용하며 브라우저 저장소에 저장하지 않습니다. 이전 프로젝트의 localStorage 로그인 기록은 새 화면에서 제거합니다. 새로고침·앱 재실행 후에는 다시 로그인합니다.
2. **기기 승인 요청**을 누르면 브라우저/OS의 WebAuthn 확인 화면이 열립니다. 검증된 공개 인증 정보만 서버에 저장되며 요청은 pending입니다. 화면에는 메모가 없습니다.
3. 운영자가 승인한 뒤 **등록 기기 확인**을 누릅니다. 서버가 저장된 승인·challenge·사이트 origin/RP ID·서명·사용자 확인을 검증한 뒤에만 자료실을 엽니다. 개인키를 앱에서 읽거나 생성 파일로 저장하지 않습니다. 표준 인증 수단이 키를 관리하며 앱은 공개 결과만 전달받습니다.
4. 확인값은 메모리에만 5분 동안 유지합니다. 각 보호 API는 소유자와 현재 서버 승인 상태를 다시 확인합니다. 만료·철회·로그아웃·오프라인에서는 자료 화면을 지우고 다시 확인하도록 합니다. 승인은 저장된 공개 인증 수단의 소유 증명이며 OS 전체의 관리 상태 검사를 구현한 것은 아닙니다.
5. **앱 설치**는 브라우저가 지원할 때 표시합니다. 설치를 해도 승인 요청과 등록 기기 확인을 별도로 해야 합니다. service worker는 공개 오프라인 안내·아이콘·manifest만 캐시합니다. API·메모·토큰·승인 결과는 캐시하지 않습니다. 따로 접속 프로그램은 설치하지 않습니다.

동기화되는 multi-device 패스키는 다른 기기에서도 같은 인증 정보가 나타날 수 있어 승인 근거로 쓰지 않습니다. 현재 정책은 singleDevice·백업되지 않은 인증 수단과 사용자 확인을 요구합니다. 지원하지 않는 PC/브라우저에서는 분명한 거부 사유가 나오며 설치 표시나 임의의 정상값으로 우회하지 않습니다. 실제 PC의 인증 수단 지원 여부는 사용자 시험이 필요합니다.

## 경로와 신뢰 경계

| 경로 | 기능 |
| --- | --- |
| GET/POST /api/device-enrollment | 서버 challenge·등록 결과 검증·pending 요청 저장 |
| GET /api/device-status | 계정의 대기/승인 건수 표시, 소유 증명 완료로 취급하지 않음 |
| GET/POST /api/device-check | 승인된 인증 수단의 새 서명 검증, 메모리 확인값 발급 |

일회용 challenge는 사용자·용도·만료 시각을 대조하고 한 번만 소비합니다. grant 원문은 서버 DB에도 저장하지 않고 해시만 저장합니다. 학생 JWT만 가진 직접 보호 API 요청은 grant가 없으면 403/device_not_registered입니다. 위조 grant·다른 사용자·철회된 승인·만료된 grant도 거부합니다. 기기 gate는 판정기의 `device_registered`와 같은 정확한 true 검사를 공유합니다. 기존 `decide(request)`의 18항목·응답 5항목·구역 규칙은 유지합니다.

서명·발급자·대상을 검증한 심판 JWT는 기존 엔진 시험 경로로 유지합니다. 일반 학생이나 클라이언트 헤더는 이 경로를 선택할 수 없습니다. 심판 JWT 경로와 브라우저 기기 확인의 실측은 구분하며 심판의 기기 검증을 브라우저에서 끝냈다고 주장하지 않습니다.

## 이전 메모/복원 콘솔 시험

11단계에서는 토큰을 localStorage에서 꺼내는 예전 함수를 사용하지 않습니다. 로그인과 등록 기기 확인을 끝낸 같은 창에서 `window.자료실요청`을 사용합니다. 이 함수는 메모·백업·복원 경로만 받아 메모리의 인증을 내부에서 붙이고 메모 본문·토큰을 출력하지 않습니다.

```js
const 결과 = await window.자료실요청('/api/notes/실제_A메모_UUID');
console.log('HTTP', 결과.status, 결과.data.error);
```

B 인증으로 A 메모는 여전히 404여야 합니다. 백업·복원은 아래 래퍼로 기존 안내를 이어갑니다.

```js
async function 복구시험(path, method='GET', body) {
  const 결과 = await window.자료실요청(path, method, body);
  console.log(결과);
  return 결과;
}
```

## 시험과 완료 구분

`npm run test:stage11`은 테스트 프로세스에서 생성한 가상 인증 수단과 실제 검증 라이브러리로 등록·서명·challenge·승인 전 거부/승인 후 허용·철회 거부를 시험합니다. 테스트 키·토큰은 프로세스 메모리에만 있으며 파일이나 로그로 내보내지 않습니다. `npm run test:stage8`, `npm run test:stage10`은 기존 소유자·구역·복원 규칙을 재확인합니다. 이 결과는 실제 사용자 PC의 WebAuthn 화면·운영 승인·심판 통과 증거가 아닙니다.

SQL 적용·실제 PC 등록·승인·기존 화면·설치·오프라인 시험은 사용자 실행 전까지 미실행입니다. SQL 적용 이후에 main 배포, 새 저장소 설치 확인, `npm run bundle` 제출 묶음 갱신을 이어갑니다.
