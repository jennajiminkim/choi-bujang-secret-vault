# 보너스 xdr-01 · 무차별 로그인 공격

## 만든 부품

- `read-alerts.mjs`: 28건 경보에서 시각·주소·계정·수준·설명만 JSONL 28줄로 읽습니다. 원본과 full_log는 출력하지 않고 지정된 비밀값 표기를 가립니다. 판단 모듈은 이 파일을 불러오지 않습니다.
- `patterns.json`: MITRE T1110.001의 비밀번호 추측, T1110.003의 비밀번호 스프레이 조건과 각각의 근거 한 줄입니다.
- `decide.mjs`: 동일 패턴 상수를 맨 위에 두고 `decide(alert)`만 내보냅니다. import·파일 작업·네트워크·호출 간 상태가 없습니다. reason은 고정 패턴 이름 또는 `일치 패턴 없음`입니다.
- `respond.mjs`: 판단을 다시 계산하고 block 후보 가운데 주소·경보 번호·시각이 유효하고 오래되지 않은 것만 추가 거부 규칙으로 저장합니다. alert는 알림만 기록합니다. `xdr/alerts.log`에는 경보 번호·판단·고정 이유만 한 줄씩 추가합니다. 원본·비밀번호·계정은 기록하지 않습니다.
- `result.json`: 기존 실행기가 만든 28건 판단과 counts입니다. 심판 정답 파일이 아닙니다.

## 학습용 판단 기준

확신도 0.85 이상은 block, 0.5 이상은 alert, 그 아래는 record입니다. 수준·건수·실패 설명·T1110 표기를 함께 봅니다. 수준 또는 MITRE 태그만으로 차단하지 않습니다. 다수 계정의 규칙적 실패는 비밀번호 추측 근거로 보며, **같은 비밀번호**라는 요약이 있어야 스프레이라고 부릅니다. 비밀번호 원문을 읽거나 비교하지 않습니다.

40건 이상, 5분 내 20건 이상, 스프레이 대상 5계정 이상, 규칙 수준 10 이상은 이 과제의 학습용 설정입니다. MITRE가 정한 보편적인 수치나 통계적으로 보정된 확률이 아닙니다. 실패 뒤 성공·불규칙 간격·명시적인 긴 시간대·부족한 근거는 알림으로 낮춥니다. 성공이 있어도 계정 침해가 없다는 증거는 아니므로 반복 실패를 정상으로 단정하지 않습니다.

이 fixture는 경보 한 건에 집계 건수 또는 공격 형태의 요약을 담습니다. 각 경보를 독립적으로 판단하며 다른 경보의 건수와 합산하지 않습니다. 단일 로그인 로그의 시간창 집계나 실제 Wazuh 수집기는 별도 연결이 필요합니다. 현재 구현은 한국어 연습 경보 형식에 맞춘 판단이며 모든 운영 로그 형식을 지원한다고 주장하지 않습니다.

## 실행과 확인

저장소 루트에서 실행합니다. 추가 패키지나 비밀키가 필요하지 않습니다.

```bash
node xdr/brute-force/read-alerts.mjs
npm run xdr:run -- brute-force
npm run xdr:respond
npm run test:xdr
```

GitHub에서 `xdr/brute-force/result.json`을 열면 counts는 **block 10, alert 9, record 9**입니다. 읽기 출력은 **28줄**입니다. 시험 8개는 원본 경보·기존 실행기를 보존하며 독립 실행, 패턴 일치, 경계 입력, 과거·미래 경보, 15분 만료, 중복 규칙, 정상 이벤트 및 정상 주소 통과를 검사합니다.

정상 이벤트 확인은 수준 3 이하·MITRE 태그 없음인 연습 경보 9건을 대상으로 했으며 block은 **0건**입니다. 이는 경보 의미에 따른 로컬 자기 점검이며 심판의 비공개 정답 확인이 아닙니다. 애매한 시도 9건은 모두 알림이고 규칙을 만들지 않았습니다.

`npm run xdr:respond`는 경보를 시각순으로 정렬하고 각 경보 시각을 시험 시계로 삼습니다. 시험 중 차단 규칙 적용은 10건입니다. `replay-deny-rules.json`과 `mode: replay` 로그로 남기고 실제 `deny-rules.json`은 변경하지 않습니다. 마지막 경보 시점에는 앞선 공격 규칙이 만료되어 시험 규칙 목록이 비어 있을 수 있습니다. 옛 경보를 오늘의 시각으로 다시 찍어 유효한 차단을 만들지 않습니다.

## ZTNA 연결과 현재 한계

`respond(alerts, {root, mode: 'live', now})`는 신뢰된 서버가 제공한 경보를 받아 `deny-rules.json`에 주소 단위 deny 규칙을 만들며 `createdAt`, `expiresAt`, `alertIds`를 붙입니다. 유효기간은 경보 발생부터 15분이고, 동일 주소의 새 명확한 공격에 한해 갱신됩니다. 읽을 때도 만료를 확인합니다. 한 저장 경로에는 한 responder 프로세스만 쓰도록 운영해야 합니다. 다중 서버 동시 저장이나 중앙 규칙 저장소는 구현 범위 밖입니다.

`createZtnaDecider(options)`는 이 저장소의 `src/decider.mjs`와 추가 IP 검사를 실제로 묶는 팩터리입니다. `withBruteForce(baseDecide, options)`는 다른 기존 정책을 묶을 수 있는 공통 어댑터입니다. 기존 deny는 유지하고, 차단 주소의 allow·step_up만 deny로 바꾸며, 차단되지 않은 요청은 기존 응답을 그대로 반환합니다. 자체적으로 allow를 만들지 않습니다.

호스트가 제공해야 하는 설정은 다음과 같습니다.

- `sourceIpForRequest(request)`: 엔진이 확인한 연결 주소를 서버 측에서 조회하는 함수. requestId 등으로 신뢰된 연결 정보와 연계합니다. 브라우저 본문·임의 헤더·`request.srcip`는 쓰지 않습니다.
- `denyResponse(request, match)`: 운영 등록부에서 허용한 reasonCode와 `xdr.brute_force.source_ip` 규칙 ID를 포함해 계약의 다섯 항목만 반환하는 함수. 코드가 새 이유 코드를 운영에 자동 등록하지 않습니다.
- `root`: 규칙 저장 경로. 운영에서는 기본 `mode: live`를 유지합니다. `mode: replay`와 `clock` 대체는 로컬 시험 전용입니다.

확인된 주소가 없거나 규칙 파일을 읽지 못하면 예외가 나며 호스트는 접속을 거부해야 합니다. 누락 정보 때문에 추가 검사를 조용히 생략하지 않습니다. 파일이 아직 없으면 추가 거부 규칙은 0건입니다.

**현재 운영 연결은 미완료입니다.** 현재 18항목 ZTNA 요청 계약에는 IP가 없고, 별도 신뢰된 주소 전달 경로나 XDR 거부 사유 등록부가 제공되지 않았습니다. 기존 엔진 진입점을 임의로 바꾸지 않았습니다. 따라서 어댑터는 만들고 시험했지만 실제 엔진이 이 팩터리를 호출하고 있다는 증거는 없습니다. Vercel `/api/notes`에도 추가 차단을 붙였다고 주장하지 않습니다.

기존 `src/decider.mjs`는 현재 `starter.deny`로 모든 요청을 거부하며 그대로입니다. 시험 정책이 정상 요청을 허용할 때 추가 검사도 정상 요청을 통과시키는 것은 검증했습니다. 현재 운영 판정기가 정상 접속을 허용한다는 뜻은 아닙니다. 엔진의 주소 전달과 사유 코드 등록이 준비되면 기존 정책의 호스트 진입점을 `createZtnaDecider(options)`의 반환 함수로 연결해야 합니다.
